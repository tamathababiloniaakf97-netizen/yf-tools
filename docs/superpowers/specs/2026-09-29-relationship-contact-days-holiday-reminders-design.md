# 人际关系：未联系天数与节日联系提示设计

## 背景与目标

现有人际关系模块已保存联系人档案、往来历史、最近联系日期、计划联系日期和生日提醒。本次增加两项轻量能力：在联系人列表直接显示距上次联系的天数，以及在重要传统节日前提示联系指定好友。设计以“看得见、不打扰、不增加维护负担”为原则，不引入关系评分、个性化联系周期或外部推送。

## 未联系天数

联系人列表中，每个联系人在姓名和关系类型附近显示一个低强度小标识：

- 今天有往来记录时显示 `0天`。
- 距最近联系 20 天时显示 `20天`。
- 超过一年仍显示实际天数，例如 `386天`，不改成“1年以上”。
- 从未记录联系时显示 `未记录`，不用联系人创建日期伪造最近联系日期。

天数以 `last_contact_at` 和当前上海日期动态计算，不在数据库重复保存。所有联系人使用同一规则，数字只作为用户查看时的参考，不产生提醒、不自动排序、不使用颜色判定关系好坏。

## 重要节日联系提示

联系人档案增加一个 **重要节日联系提示** 开关。开关同时适用于春节、端午节和中秋节，不为每个节日分别配置。新增联系人和已有联系人都默认关闭，避免迁移后突然出现大量提示；用户只对希望维护的联系人主动开启。

节日日期基于中国农历计算：春节为农历正月初一，端午节为农历五月初五，中秋节为农历八月十五。计算复用现有生日模块已使用的 `Intl.DateTimeFormat('zh-CN-u-ca-chinese')` 能力，不增加新的农历依赖或每年手工维护日期表。

每个节日的提示窗口从节日前 3 天开始，到节日当天结束。窗口期内在站内提醒中显示，例如“中秋将至，考虑联系胡琴”。提示指向该联系人详情，同一联系人在同一节日窗口最多显示一条。

## 提示的自动消失

节日提示不增加“完成”按钮或独立状态。用户在提示窗口内为联系人新增任意类型的往来记录后，该联系人当次节日提示自动消失。判断依据是 `last_contact_at` 不早于当次提示窗口起始日；这与现有“新增往来同步更新最近联系日期”的逻辑一致。

用户若在窗口前联系过对方，窗口开始后仍会显示节日提示；这是有意设计，因为此功能确认的是“本次节日是否已联系”，而不是“最近总体是否联系过”。

## 数据与兼容性

数据库只在 `contacts` 表增加非空布尔字段 `holiday_contact_reminder_enabled`，默认为 `false`。迁移为增量变更，不删除、改名或重写已有字段和往来历史，因此现有人际关系数据不会丢失。新字段继续受现有联系人 RLS 策略保护。

类型定义、表单校验和 API 读写同步增加该开关。节日提示并入现有站内提醒聚合逻辑，不单独建表、不创建持久化提醒记录。

## 验收标准

- 联系人列表对所有人显示动态计算的未联系天数，从未联系者显示“未记录”。
- 新增和已有联系人的节日提示默认关闭，用户可在联系人编辑中开启。
- 开启后，春节、端午和中秋各自在节前 3 天至当天显示站内联系提示。
- 窗口内新增往来记录后，当次节日提示消失；不需要另外点击完成。
- 关闭开关的联系人不产生节日提示，其他计划联系和生日提醒不受影响。
- 迁移后原有联系人、生日数据和往来历史均保留且可正常读取。

## 不在本次范围

- 微信、短信、邮件、手机系统级推送或自动发消息。
- 节日祝福语生成、送礼建议或群发功能。
- 每个节日的独立开关、自定义节日、个性化提前天数或每个联系人的联系周期。
- 根据未联系天数生成待办、健康分、红黄绿警报或自动排序。
